How the system fits together

Numbered circles show the order of events; boxed numbers are messages sent (see table below).

10 s check interval~1 s per check~20 s CAPTCHA solve (12–40 s)~5 s slot to confirmed booking~1 s submit when already parked

Every message the system sends

BadgeWhenWhat it says (shortened)
1Slot window opens“✅ Long-stay visa (D-visa) application is now available for … Embassy … Book here: link”. Call says: “Estonia visa slot is now available. Check Telegram and book immediately.”
2Monitor’s own check fails“⚠️ Estonia visa monitor is FAILING and cannot currently check the booking calendar. Error: …” Sent once, then silent for 1.5 h. Never rings the phone.
3Daemon starts or stops“🚀 booker daemon started” · “🛑 booker daemon stopped”
4Parked seat obtained“🎫 Seat acquired … dates on the calendar … now parked, polling every 2 s”
5Free times seen“🕒 Slots visible at … on date” plus the times. Sent on change, at most every 30 s.
6Booking confirmed“✅ APPOINTMENT BOOKED” with embassy, date, applicant and reference (or “BOOKED AN EARLIER APPOINTMENT”).
7CAPTCHA can’t be solved“❌ Slot found … but the booking CAPTCHA could not be solved. Check the portal manually.”
8Submitted, no confirmation“⚠️ Submitted a booking … could not confirm success. CHECK THE PORTAL MANUALLY.”
9Parked seat looks stale“⚠️ monitor reported D-visa available Ns ago, but the parked seat returned zero slots … starting reacquisition”
10Solver balance or limit“⚠️ CapSolver balance is $x (below $1) …” (repeats hourly) · “⚠️ … hit its CAPTCHA rate limit … solving paused”
11Test runs“🧪 Test message from the … monitor” · “🧪 DRY RUN: would have booked … No real submit was made.”

All messages go via Telegram (slot alert also places a call) and end with a “Sent from GCP” signature (configurable) so you know which machine sent them. Red-edged rows are warnings you should act on; Program 1 failures never trigger phone calls.
